# Фильтры окон: даташит

Как SSH Snippets Keeper решает, в какие окна разрешено вводить текст сниппетов, и какие инструменты помогают диагностировать «пропавшие терминалы».

## Цепочка проверки (гейт ввода)

Вердикт по окну принимается в три шага, строго по порядку:

1. **Whitelist процессов** — `TWindowMonitor.IsProcessAllowed` (Automation\WindowMonitor.pas).
   Список собирается из галочек раздела «Разрешённые приложения» настроек
   (фоновый exe в нижнем регистре). Пустой список = не разрешено ни одному процессу.
   Окна выключенных приложений отсеиваются здесь.
2. **Глобальный запрет (deny-набор)** — `TProcessProfile.EvaluateGlobalDeny` (Automation\ProcessProfile.pas).
   Включённые правила `Settings → GlobalTitleDenyRules` проверяются по RegEx заголовка окна
   (опция «учитывать регистр» — на каждое правило). Битый шаблон правила не блокирует и не падает.
   Сработавшее правило перекрывает любые профили.
3. **Профиль процесса** — `TProcessProfile.MatchesWindow`, общий код с `EvaluateWindowFilters`.
   Нет профиля для exe → окно разрешено. Профиль выключен → без фильтров.
   Включённый профиль применяет фильтры по порядку:
   - `TitleIncludeRegex` — заголовок обязан совпасть (пусто = любой заголовок);
   - `TitleExcludeRegex` — совпавший заголовок блокируется;
   - `WindowClasses` — **жёстный** фильтр: непустой список разрешает только точные
     совпадения класса окна (без учёта регистра). Пустой список = любые окна процесса.

Итог: окно проходит, если процесс в whitelist, ни одно deny-правило не совпало
и все включённые фильтры профиля пропустили.

> Типичная ловушка: `WindowClasses` со значением из другого терминала
> (например, `CMoTTY` — класс KiTTY — у профиля MobaXterm, чей реальный класс
> `TMobaXtermForm`) молча скрывает все окна процесса из истории и выбора цели.

## Где живут настройки

- Файл настроек резолвится через `ResolvePath` (Common\Common.Helpers.pas):
  папка exe; в dev-режиме — `Assets\ExeData` через fallback `..\..\..\Assets\ExeData`.
- Профили приложений: `AllowedApplications.Items[i]` — `ExeName`, `Enabled`,
  `TitleIncludeRegex`, `TitleExcludeRegex`, `WindowClasses`.
- Deny-набор: `GlobalTitleDenyRules.Items[]` — `Name`, `Pattern`, `CaseSensitive`, `Enabled`.

## Контроль до и после настройки фильтров

| Инструмент | Где | Что показывает |
|---|---|---|
| Живое превью профиля | Настройки → Разрешённые → «Профиль…» | Каждое открытое окно процесса: пройдёт/блокируется и каким фильтром (include, exclude, класс). Счётчик «Окон: N, пройдёт: M» подсвечивается красным, если не пройдёт ни одно. |
| Санити-чек при сохранении | Кнопка «Сохранить» настроек | Предупреждение, если класс-фильтр включённого приложения не совпадёт ни с одним открытым окном процесса (окно исчезнет из списков). Include/exclude-фильтры, блокирующие всё, — намеренный сценарий и не проверяются. |
| Диагностика фильтров | Настройки → «Диагностика…», либо клик по подсказке пустого списка в выборе терминала | Таблица всех открытых окон включённых процессов со слоем отсечения: deny-правило (с именем правила), include, exclude, класс окон. Оценивает черновик настроек (в настройках) или сохранённые настройки (из выбора терминала). |
| Подсказка пустого списка | Окно выбора терминала | Если история разрешённых окон пуста — подсказка о возможных фильтрах и переход в диагностику. |

## Распространённые сценарии

- **Терминал пропал из выбора цели.** Откройте диагностику: строка окна либо
  отсутствует (процесс не в whitelist / окно невидимо), либо помечена слоем
  блокировки. Частая причина — класс окна в профиле не совпадает с реальным.
  Точный класс окна видно в менеджере терминалов.
- **Нужно ограничить ввод одной вкладкой.** Используйте include/exclude по заголовку;
  полный блок по этим фильтрам допустим и санити-чеком не прерывается.
- **Запрет ввода везде по маске заголовка.** Раздел deny-набора: правила блокируют
  ввод поверх всех профилей разрешённых приложений.
